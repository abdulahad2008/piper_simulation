# Phase 1 audit: simulation correctness, sizes, stopping time

Kitchen-hazard study (hot pan first, knife second). Branch `kitchen-hazard-phase1`,
base `main` @ `6286bfe`. Written 30 Oct 2026. Every number below comes from a
committed script run in this branch or from a source that was opened, not from
a search snippet. Confidence tags: [Certain] measured or read directly;
[Likely] inferred or from a secondary copy of a primary source; [Guessing] stated as such.

## 1. Bugs found and fixed

### 1.1 Human arm segments were 1.07 m long (fixed)

`piper_rl/human_aware_env.py::_quat_from_z_axis` normalised its argument in
place (`np.asarray` returns the caller's array; `v /= norm`). `_set_segment`
then measured the segment from the same array, so every capsule half-length
was `0.5 * |unit vector| = 0.5 m`. The upper arm and forearm were 1.00 m long
plus end caps, whatever the joint points said. Present from `9c1175b`
(5 Aug 2026) to `6286bfe` [Certain, read from the code and measured].

Measured on `6286bfe` with `tests/test_scene_validity.py`, 1000 kinematic
episodes per preset, 201 samples per episode (20 Hz over 10 s):

| preset | worst drawn-length error | lowest point over the table footprint | penetration of static geometry |
|---|---|---|---|
| all ten presets | 834–868 mm (drawn 1.000 m vs joint distance 0.13–0.21 m) | z = −0.07 m (table top is 0.20 m, floor 0.00 m) | table: yes, every preset; floor: yes, every preset, 26–57 mm at t = 0 in the parked pose |

The parked arm (no-human episodes) also pokes through the floor, because the
1 m forearm points downwards from the elbow. It does not reach the robot or the
table footprint in the parked pose, which is why the no-human results were not
affected (see 1.4).

Fix: `v = np.array(direction, dtype=np.float64, copy=True)`. One line, as diagnosed before this session.

**Reproducibility note [Certain]:** on 30 Oct no branch on GitHub carried this
fix (`git ls-remote`: main, sharp-tools, final-eval-2026-10, feature/human-aware-pick-place,
phase0-retrained-solver-results, precision-floor-instrumentation). If retraining
with "the corrected arm" is running on the training PC, it runs on an
uncommitted local edit. Diff that working copy against this branch before
trusting those runs, and commit the same line there.

### 1.2 The knife could not touch the person (fixed)

`agilex_piper/piper_knife.xml` (generated by `piper_rl/scripts/make_knife_scene.py`)
gave both knife geoms `contype="0" conaffinity="0"`, by design in October ("the
hazard wrapper measures it geometrically"). A blunt hit with the handle or
spine therefore never produced a contact. For the kitchen study the held object
must be touchable, so the knife now has `contype="4" conaffinity="2"`: it
collides with the person's capsules (contype 2, conaffinity 3) and with nothing
else (robot links, table, cup are all 1/1). Robot, table and object contacts
are unchanged [Certain, bitmask test in `piper_rl/hazard/tests/test_knife_scene.py`].

Still open: the environment's `human_collision` flag only counts contacts
between the person and `robot_geoms` (arm links and finger pads). A knife–person
contact is now a real MuJoCo contact but is not yet counted by the env. That
is Phase 3 box 4 (contact levels), not a Phase 1 fix.

### 1.3 Not a bug, but a documentation error: the arm's top speed is 0.17–0.30 m/s, not 0.60 m/s

See section 3. The `max_step_dist = 0.03 m` at 20 Hz is the nominal 0.60 m/s;
the two-iteration damped IK realises about 13.4 mm of each 30 mm step, so a
full action moves the TCP at about 0.27 m/s from the start pose. No clamp
fires. Every document that says "0.6 m/s gripper speed limit" is describing
the cap, not the behaviour.

Two of the eight checks you listed are regression guards, not bug detectors,
and I have labelled them so rather than pretend they discriminate. The
no-human check is stronger than "success rate unchanged": the robot's joint
trajectory is bitwise identical whether the parked arm is in place or moved
10 m away, for the pre-registered no-human seeds, so no edit to the arm
geometry can change the no-human success rate.

Side effect of the fix on existing tests: `piper_rl/hazard/tests/test_knife_scene.py`
asserted the old non-colliding masks; updated. `tests/test_human_aware_env.py::test_state_plus_rgb_extends_only_state_and_renders_headless`
fails in this container with and without the fix (no OpenGL context; the
HANDOFF already notes it needs OSMesa).

### 1.5 Finding, not fixed: the committed evaluation numbers do not reproduce on another machine

`piper_rl/scripts/evaluate_human_aware.py --experiment no-human --episodes 200 --seed 30000`
with `models/human_aware_curriculum_hold_s3.zip`, fixed arm, on this Linux
container (Python 3.13, torch 2.15.0+cpu): task success **83.5 %** against
**91.0 %** in the committed Windows CSV (`results/human_aware_curriculum_hold_s3/heldout/no_human.csv`).
Per-episode outcome agrees in 87.5 % of the 200 seeds; no episode has the same
reward to 1e-6, and the median per-episode reward difference is 1.5. The arm
fix is not the cause: the regression guard shows the no-human trajectory is
bitwise identical with the arm in place or moved 10 m away. The cause is
floating-point divergence in the policy's forward pass between torch builds
and CPUs, amplified by contact dynamics [Likely; consistent with the earlier
note of "up to 8 points" between Linux/numpy and Windows/torch re-runs].

Consequences: (a) every number in the paper is a number for one machine and
one torch build; say so; (b) only comparisons run on the same machine in the
same session are valid, which the earlier notes already require; (c) a
platform-stable actor (export the SAC actor to float64 numpy with no fused
kernels) would make the evaluations reproducible anywhere. Not done in Phase 1
because it changes the evaluation path; it is a candidate for Phase 2.

### 2.5 Standards for Phase 3 (opened, values noted for later use)

- **ISO/TS 15066** body model: hand/fingers max permissible force 140 N (spring 75 N/mm, effective mass 0.6 kg); lower arm 160 N (40 N/mm, 2 kg); upper arm 150 N (30 N/mm, 3 kg). Read from Table 1 of arXiv 2311.13814 (secondary) [Likely]. Per-region quasi-static pressures from the Fraunhofer IFF slides (NIST-hosted): back of hand 200 N/cm² / 140 N, forearm muscle 180 N/cm² / 90 N, deltoid 190 N/cm² / 70 N, marked preliminary. The factor-of-two rule for transient contact is widely reported but neither page states it: [Likely], verify in the TS itself before the paper.
- **ISO 10218-1/-2:2025** replace the 2011 editions and absorb the collaborative-application content of ISO/TS 15066 (A3 FAQ, 20 Mar 2025) [Likely; iso.org page not opened]. Cite the 2025 editions as the current robot-safety standard.
- **ISO 13855** (EN ISO 13855:2024): K = 2.0 m/s hand/arm, 1.6 m/s walking (Leuze page) [Likely].
- **Hot surfaces:** the IEEE PSES slide deck quotes BS EN 13202:2000 thresholds for uncoated metal: 65 °C at 1 s, 55 °C at 10 s, 48 °C at 10 min. ISO 13732-1 gives the same family of curves with a 65–70 °C spread at 1 s [Likely; the ISO text was not opened]. A pan on a stove is far above either, so any contact with the pan's base or walls is severe.

## 3. Stopping time and distance (measured)

`piper_rl/scripts/measure_stopping.py`, no-human scene, standard start pose,
0.4 s of full command in eight Cartesian directions, then a stop command, TCP
recorded at 500 Hz. "Stopped" = TCP speed below 2 cm/s for the rest of the 2 s window.

| stop command | steady speed before the stop | stopping time | TCP travel to stop | travel at 0.2 s / 1 s after the command |
|---|---|---|---|---|
| hold the measured joint position (scripted controller) | 0.17–0.30 m/s | 0.05–0.26 s | 2–6 mm | 2–6 mm / 1–3 mm |
| zero action (what a learned policy can do) | same | 0.11 s to never within 2 s (creep at 2–4 cm/s) | 12–23 mm | 13–19 mm / 14–23 mm |

Reaction time: one control period, 0.05 s (a command issued at tick k acts
during tick k's 25 substeps). Sensing is perfect except in the OOD suite
(150 ms observation latency).

What this changes in the plan [Certain for the simulator]:

1. The plan assumed 0.1 s stopping time. The scripted stop needs up to 0.26 s to
   fall below 2 cm/s; use **T_s = 0.30 s, T_r = 0.05 s, S_s = 6 mm** in the
   ISO/TS 15066 distance. A zero-action stop is not a stop: the TCP keeps
   creeping because the IK's null-space orientation servo leaks into position
   through the damping. Any learned "stop" needs a hold mode or the creep
   must be accepted and reported.
2. The robot speed term should use the **realised 0.30 m/s**, not 0.60 m/s.
3. Protective distance S = v_h (T_r + T_s) + v_r T_r + S_s with the measured values:

| hand speed | sensing delay | S (measured T_s = 0.30 s) | S in the plan (T_s = 0.10 s) |
|---|---|---|---|
| 0.40 m/s | none | 0.16 m | 0.12 m |
| 0.40 m/s | 150 ms | 0.27 m | 0.27 m |
| 2.0 m/s | none | 0.72 m | 0.36 m |
| 2.0 m/s | 150 ms | 1.07 m | 0.75 m |

The 25 cm intrusion zone still covers the 0.4 m/s cases. For the fast-hand
set the stop distance exceeds the arm's 0.63 m reach even with perfect
sensing, so a stopping controller cannot be made safe there; that is the
case the paper should show, not hide.

## 4. Decisions for you

1. Arm radii (thin by 1–2 cm) and segment lengths (upper arm short, reach too
   long): keep the corrected interpolated arm as decided, or move to a
   fixed-length two-link arm for the new kitchen study only? The earlier cup
   results stay on the corrected interpolated arm either way.
2. Pan size: 24 cm / 1.1 kg welded (realistic kitchen, unrealistic grip) or
   16–20 cm / 0.5 kg (realistic grip)?
3. Scale fix for figures (floor at −0.70 m): renders only, or also in the
   training scenes?
4. Stop parameters: adopt T_s = 0.30 s, T_r = 0.05 s, v_r = 0.30 m/s, S_s = 6 mm?
